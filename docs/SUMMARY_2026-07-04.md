## Problems hit and how they were resolved

1. **Invalid provider argument** — `aws_batch_compute_environment` needs
   `compute_environment_name`, not `name` (AWS provider v5). Fixed.

2. **Compute environment went INVALID** —
   `SpotFleetRequestConfig.IamFleetRole is invalid`. The Terraform had reused the
   Batch *service* role as the Spot fleet role. Added a dedicated Spot fleet role
   trusting `spotfleet.amazonaws.com` with `AmazonEC2SpotFleetTaggingRole`.

3. **Jobs stuck in RUNNABLE, no instances launched (root blocker)** — the Spot
   fleet errored with *"The specified instance type is not eligible for Free
   Tier."* This AWS account is on the **new AWS Free Tier plan**, which only
   permits free-tier-eligible instance types (max **2 vCPU / 8 GB**, e.g.
   `m7i-flex.large`). The pipeline's c5/r5 request (8 vCPU / 16 GB) could never
   be placed. Confirmed the Spot vCPU quota in the region is only 5.

   **Resolution (chosen path): keep AWS-first, shrink to fit Free Tier.**
   - Reconfigured the compute environment to **on-demand EC2**,
     `allocation_strategy = BEST_FIT_PROGRESSIVE`, `instance_type =
     ["m7i-flex.large"]`, `max_vcpus = 8`. This removes the Spot fleet entirely.
   - Lowered every pipeline stage in `nextflow.config` to **2 vCPU / 6 GB** so
     each job fits a free-tier instance. Fine for the small chr21 test data.
   - Removed the now-unused Spot fleet role from Terraform.

4. **Terraform state drift** — a `terraform apply` was killed by a 2-minute
   command timeout *after* it created the job queue in AWS but *before* saving it
   to state. The retry then failed with `CreateJobQueue: 409 Object already
   exists`, and the queue was live in AWS but untracked.
   **Fix:** `terraform import` of the queue back into state, then a benign
   in-place normalization (`compute_environments` → `compute_environment_order`).
   Final `terraform plan` is clean.
